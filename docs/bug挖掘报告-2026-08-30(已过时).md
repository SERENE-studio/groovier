# Groovier Bug 挖掘报告(2026-08-30)

审查方式:4 路 subagent 并行只读审查(coremod 转换层 / api+command+engine / sandbox 安全 / override+refer+registry+kubejs),主会话对关键条目逐行复核,并对可疑判据做了 jar 反汇编实证(asm-9.8、groovy-4.0.33、mixin-0.8.5)。**未修改任何代码。**

与上一份《核查报告-2026-08-30》的关系:该报告所列条目经逐条回读源码,**全部仍未修复,继续有效**;本报告按层统一编号,凡与上轮重合的均标注(=上轮编号)。

结论:**确认 bug 共 36 项(高危 6、中危 15、低危 15),远超 5 项门槛,不满足"无 bug 证明文档"的豁免条件。**

## 一、高危(6)

### G1 【沙箱逃逸】GroovierClassLoader 不在黑名单 → 脚本二次编译完全绕过沙箱
- `sandbox/security/GroovySecurityManager.java` L54-55, L104-106;关联 `engine/GroovierClassLoader.java` L20, L25
- 黑名单用 `contains` 精确匹配 FQN,只 ban 了 `groovy.lang.GroovyClassLoader`,而 public 的子类 `com.bluesky.groovier.engine.GroovierClassLoader` 不命中,包也不在 bannedPackages。脚本可用它 + 无定制器的 `CompilerConfiguration` 编译任意黑名单代码——新产物完全不走 GroovierCompiler。
- 攻击:`new GroovierClassLoader(this.class.classLoader, new CompilerConfiguration()).parseClass('"cmd /c whoami".execute()')`

### G2 【沙箱逃逸】运行时守卫唯一拦截点可被公开 Groovy API 整体卸载
- `sandbox/security/GrSMetaClassCreationHandle.java` L21-34;关联 `GroovierSandbox.java` L58
- 守卫只挂在 `createNormalMetaClass`(registry 缓存 miss 时)。`MetaClassRegistry.setMetaClassCreationHandle / setMetaClass / removeMetaClass` 均为 public(groovy-4.0.33 javap 实证),相关类全部不在黑名单。三行代码即可重建正常 MetaClass,黑名单类调用全部放行。SPEC §2.5 "EMC 无法覆盖黑名单类"仅对 `Runtime.metaClass.x = ...` 语法成立,显式 API 路径无拦截点。

### G3 【沙箱逃逸】安全组件自身对脚本零防护,`unBanClass` 可直接调用;`@GroovyBlacklist` 全项目零使用
- `sandbox/security/GroovySecurityManager.java` L34, L64-82
- `GroovySecurityManager.INSTANCE` 公开且不在黑名单,public 方法 `unBanClass/banPackage/banClass/banMethods` 可被脚本调用改写黑名单。grep 全源码证实 `@GroovyBlacklist` 除自身定义外零处实际使用,SPEC §2.5 的内部 API 标记机制未落地。白名单优先一票通过,编译期与运行时同时放行。
- 同根因变体(中):`ScriptManager` 构造器副作用注册 `GlobalManager.setOnChange`,脚本 `new ScriptManager()` 即可永久废掉动态启停回调(`ScriptManager.java` L58)。

### G4 【沙箱逃逸】实例调用分支不比对 bannedMethods + OBJECT_TYPE 短路(=上轮 H2,有补充)
- `sandbox/transformer/GroovierTransformer.java` L56-66(主会话复核属实)
- 实例分支只查 receiver 黑名单类与 `String.execute` 字面名;`bannedMethods` 其余条目(`ProcessGroovyMethods.execute`、`Thread.stop/suspend/resume`)完全不参与。补充实证:L59 对 `OBJECT_TYPE` receiver 直接 return,连类检查都跳过。
- 攻击:`["bash","-c","whoami"].execute()`(DGM `ProcessGroovyMethods.execute(List)` 创建进程);`def o = ["cmd","/c","x"]; o.execute()` 同理。

### G5 【沙箱逃逸】包黑名单缺 `java.nio.channels` / `com.sun.`(=上轮 H3)
- `sandbox/security/GroovySecurityManager.java` L47-52
- bannedPackages 仅 `java.net/javax.net/java.rmi/java.security/groovy.grape/sun.`。`java.nio.channels.ServerSocketChannel.open().bind(null).accept()` 全程无 `java.net` 字面引用,编译期与运行期均放行,完整网络出口。`com.sun.net.httpserver` 同理。

### G6 【类加载崩溃】钉子 wrapper `maxStack = 4` 硬编码不足 → 目标类 VerifyError
- `coremod/PinningTransformer.java` L158(声明),L223-228、L236-247(溢出点,主会话复核属实)
- 三处真实峰值 > 4:① 2d 段非静态调原方法 receiver+参数槽,`(IIII)V` 即 5,long/double 参数更宽;② 2e 段非 void 返回为 long/double 时 LLOAD 压 2 槽,key+thiz+args(3)+2 = 5;③ 静态原方法 `(JJJ)V` = 6。JVMS 明确 long/double 占 2 槽。L255 的 Analyzer 自检不校验 maxStack 与实际一致性。
- 后果:钉住任何此类方法,类首次链接即 `VerifyError: Insufficient maximum stack size`,类加载失败。

## 五、已排除的误报(实证备忘,勿"修复")

1. **mixinMapping 点分匹配**:mixin-0.8.5 反汇编实证 key 填充前 `replace('/','.')`,现有 `MixinRegistryProxy` 点分匹配正确,勿改。
2. **ASM itf 误报已确认是真 bug 而非误报**(见 M1),但反向注意:类的 private 实例方法用 INVOKEVIRTUAL 在 Nestmates 后合法(HotSpot jtreg `TestMethodSelection`),勿大面积改 invokespecial。
3. **javax.script + Rhino 逃逸假设不成立**:`libs/rhino-*.jar` 经 jar tf 证实无 `ScriptEngineFactory` SPI 文件,发现不了,不报。
4. **编译选项旁路不成立**:grep 证实无沙箱+CompileStatic 的 `compilerConfig()` 唯一调用方为 OverrideManager(可信路径);脚本路径统一走含 GroovierCompiler 的 createConfig,无旁路。
5. **AST 遍历覆盖面完整**(groovy-4.0.33 javap 实证):`visitField` 会 transform 初始值,`visitClosureExpression`/`visitLambdaExpression` 递归,GroovierTransformer 无节点类型遗漏逃逸;结构性缺陷在 G1-G5 而非遍历面。
6. **postProcess hook 字节码**:`CoprocessorInjector` 峰值栈 4/locals 4、唯一 F_FULL 帧描述、构造器 maxs 逐指令验证通过。

## 六、修复优先级建议
